SEER Instruction Set Architecture · v17 · March 2026
One binary.
Every device.

SEER is a fixed-width, structurally-uniform ISA designed from first principles — covering MCU, CPU, and GPU execution in a single binary, with AI legibility and compiler simplicity as first-class goals.

Core Thesis
Every ISA since x86 has accumulated complexity. SEER starts with the question: what would an instruction set look like if it were designed for the constraints of 2026 — AI-assisted programming, heterogeneous execution, and formal verification?
The answer: 256 opcodes, 8 bytes each, tier-routed by a single bitmask operation, with the universal op table giving every operation a globally consistent column position across all instruction groups.

Architecture · Overview
How SEER is structured
The top byte of every instruction encodes everything the hardware needs to route, decode, and latency-schedule the instruction — with no lookup tables required.

The Opcode Byte

Byte 0 of every SEER instruction is the opcode. It splits cleanly into two nibbles: the high nibble selects the row (instruction group), the low nibble selects the column (operation within that group). The universal op table means the same low nibble means the same operation across rows where applicable.

Tier Model: OPU → APU → FPU → GPU

The top two bits of every opcode byte fully identify the execution tier. No extra bits, no lookup tables. Any partition of these four tiers into physical units is a valid SEER chip — the ISA, compiler, and all compiled binaries are unaffected. Only the routing table changes.

The 15 valid hardware configurations

Four tiers produce 15 distinct non-empty partitions. Every one is a valid SEER chip. The routing table is the only hardware artifact that changes between them.

The OPU always-on island

Key insight: Rows 0x00–0x3F cover everything needed to run an OS kernel: interrupt handling, memory management, system calls, control flow, loads and stores. That silicon footprint is tiny. An always-on OPU running at 1–10 MHz on microwatt power handles all standby duties while the APU, FPU, and GPU sleep — no separate microcontroller firmware, no separate binary, no context switch to wake them.

Binary portability guarantee

The same compiled binary runs on a monolithic single-core (all tiers merged) or a four-unit heterogeneous chip (each tier on dedicated silicon). The compiler targets tiers, not physical units. The routing table — four entries, one shift, one AND — is the complete scheduler.

Universal Op Table

The low nibble of the opcode encodes a consistent operation across all rows that support arithmetic. This is SEER's most distinctive property: column B always means "add-like", column F always means "divide-like", regardless of which row you're in.

Trap Vectors

0x06 — Alignment fault: natural alignment required for all MEMS ops; misalignment raises this trap.
0x07 — Arithmetic trap: wrctrl on read-only ctrl reg IDs (0x10+); divmod with rs2==rd.
0x80 — Syscall (ecall): syscall number in r0, args in r1–r15.
0x81 — Debug trap (ebreak): user-accessible; for debugger integration.
vxchg precise exception: operation abandoned with no state modified on trap — all-or-nothing group save/restore.
tlbi implicit sfence: both tlbi rs=ZR (full TLB flush) and tlbi rs=VA (single page) carry an implicit store-buffer drain + sfence in both modes.

Default is free: 0x00 = process node, indent 0, default routing, no else. Every 0x1_ instruction with byte 7 left as 0x00 is a plain body instruction — invisible to the graph, zero cost. The field is always present and always read; it just has no structural effect when zero.

A tool scanning only byte 7 of branch instructions reconstructs this entire graph in one pass.

Branch Offset Shrinkage

The byte is free. jmp offset shrinks 56-bit → 48-bit (±140 TB). Conditional branches shrink 40-bit → 32-bit (±2 GB). No real program spans 2 GB. The recovered byte funds the entire graph encoding at zero ISA cost — and the tighter bitfields are a strict improvement independently.

Why It Matters

The fundamental problem: Every ISA since the 1950s separates program structure from program behavior. Compilers know the CFG when emitting code — then discard it. Debuggers, profilers, JITs, and security tools each reconstruct it independently, redundantly, imperfectly, at runtime cost. SEER encodes structure permanently in the binary at the exact points where it is semantically meaningful: the control-flow instructions of row 0x1_.

Security — Hardware CFI

Valid branch targets are node entries. Any branch to a non-entry address is an illegal fetch caught before decode. Hardware-enforced CFI with zero runtime overhead — no shadow stack, no checks, no 5–10% tax.

Profiling

Every sampled PC maps immediately to node type and structural position. Loop bodies, decisions, and merge nodes identified from one bit-read. No stack unwinding, no instrumentation, no DWARF.

Branch Prediction

The predictor sees loop back-edge, always-taken fork, or conditional decision from a static bit before any execution history. First-iteration prediction is structurally informed, not guesswork.

JIT Compilation

Complete CFG readable in one linear scan of cold binary. No tracing phase, no instrumentation. Loop bodies, rare branches, and merge points immediately visible from the node type field.

Debugging

Breakpoints are node table flag flips — no code mutation, no cache invalidation, no race conditions. Conditional breakpoints are counters in the table entry.

Substrate Independence

Same binary: native SEER executable and IVX program simultaneously. A CPU executes the opcodes. A graph engine reads only the NodeID bytes. Both descriptions complete, no duplication.

Design Claim · 01
Address Materialization
Loading a 48-bit address or constant should cost one instruction. On every other ISA it costs two to four. SEER's VA space was deliberately sized to make this possible.

Design Claim · 02
Register Spill
255 GP registers encoded in a full byte. Any SEER implementation can expose 8 to 255 — same binary, same ISA. Drag the slider to simulate any register count.

A spill occurs when the compiler runs out of registers and stores a live value to the stack, then reloads it. Each spill = 1 store + 1 load = 3–40 cycles of overhead depending on cache level.

Why register count is the dominant spill factor

The byte-alignment argument. Objection to 255 registers: "you're wasting register address bits on hardware with fewer physical registers." The answer: SEER requires byte-aligned fields throughout — every register operand occupies exactly one byte regardless. On hardware with 16 physical registers, the top 4 bits of that byte would be padding. SEER puts them to work instead. The "wasted bits" were never available to spend elsewhere. Maxing out the register space to 255 is free.
Design Claim · 03
Heterogeneous Dispatch
A single bitmask check at decode time replaces the entire CPU-GPU runtime stack. The question is not just which workloads become faster — it's which ones become viable at all.

Dispatch overhead = everything between a CPU deciding to run something on another unit and that unit actually starting. CUDA: 5–50 µs. SEER bitmask routing: one AND + compare, ~2 ns theoretical.

Caveats

SEER figure is theoretical. The ~2 ns estimate assumes the bitmask routing is implemented in hardware and that the target unit has a shared register file or coherent memory accessible without copying. Real silicon would add interconnect latency.
CUDA/OpenCL overhead is measured. The 5–50 µs range reflects real launch overhead on modern discrete GPUs, varying by driver, kernel complexity, and argument marshalling.
The viability point matters more than the speed point. Fine-grained tasks (sort 200 elements, hash 32 bytes, compress one block) are currently CPU-only not because GPUs are slow at them but because dispatch overhead exceeds their runtime. Near-zero dispatch makes these economical to offload.
