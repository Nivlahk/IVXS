SEER Instruction Set Architecture · v19 · 2026
One binary.
Every device.

SEER is a fixed-width, structurally-uniform ISA designed from first principles — covering MCU, CPU, and GPU execution in a single binary, with deterministic, non-speculative execution and hardware-enforced memory safety as first-class goals alongside AI legibility and compiler simplicity.

Core Thesis
Every commercial processor since the 1990s has bought performance with speculation — branch prediction, out-of-order execution, variable-latency memory — and paid for it with Spectre- and Meltdown-class timing side-channels that are structural consequences of speculating at all, not bugs to be patched. SEER starts with a different question: what would a processor look like if it never speculated, and treated memory safety as a hardware guarantee instead of a software convention?
The answer, on SEER's core execution path: every instruction resolves in one fixed cycle — no branch prediction, no speculative state to unwind, no variable-latency memory access for an attacker to time. Every memory reference is authenticated against a hardware capability token and tiny pointer at the point of access, never trusted from software. The same byte-aligned, tier-routable structure — 256 opcodes, 4 bytes each, routed by a single decode-time bitmask — that makes SEER simple to compile for is what makes it exhaustively verifiable: a fixed point in the design space built for real-time, safety-critical, security-sensitive embedded systems, where predictable timing is a certification requirement, not a nice-to-have.

The Opcode Byte

Byte 0 of every SEER instruction is the opcode. It splits cleanly into two nibbles: the high nibble selects the row (instruction group), the low nibble selects the column (operation within that group). The universal op table means the same low nibble means the same operation across rows where applicable.

Tier Model: OPU → APU → FPU → GPU

How Structure Lives in the Opcode

Every ISA since the 1950s separates program structure from program behavior. Compilers know the CFG when emitting code — then discard it. Debuggers, profilers, JITs, and security tools each reconstruct it independently, redundantly, imperfectly, at runtime cost.

SEER solves this differently. The Vertex graph structure is recoverable from the opcode sequence itself through bitmask operations — no separate annotation required:

Node Type → Opcode
connector node → nop (0x10) — the only valid jump target
decision node → 0x1B–0x1F — conditional branches
function node → jmpr (0x19) — indirect call/jump
syscall node → ecall (0x12)
process node → everything else
Bitmask Detection
opcode == 0x10 → connector (valid jump target)
(opcode & 0xF8) == 0x18 → control flow
(opcode & 0xFC) == 0x1C → conditional branch
opcode == 0x19 → indirect jump/call
opcode == 0x12 → syscall
CFI is a single comparison: valid branch targets must be connector nodes (nop, opcode 0x10). The hardware checks target_opcode == 0x10 before decode. No node table lookup, no byte 7 read, no shadow stack. One byte comparison — that is the entire CFI mechanism.

The CN Counter

The hardware maintains a Connector Node counter (CN) alongside the PC. It increments every time a nop (0x10) is fetched. Branches encode their target as a signed CN-relative offset — not a byte offset.

Old model (byte offset)
jlt r1, r2, -0x34
→ "jump back 52 bytes"
→ CFI must verify target is a node entry
→ extra hardware check required
New model (CN offset)
jlt r1, r2, -2
→ "jump back 2 connector nodes"
→ target is a connector node by definition
→ CFI is a bounds check, not a type check

CN counter hardware

The fetch unit increments CN when it sees opcode 0x10. This is one extra gate on the existing fetch path — the fetch unit already reads byte 0 for opcode dispatch. CN is saved/restored as part of trap state alongside PC.

CN table at load time

The linker/loader populates a static CN table mapping CN index → PC. One scan of the binary, indexed by nop position. The table is read-only at runtime. Hardware resolves branch targets in one table lookup.

Design Claim · 01
Constant Materialization
Under tiny pointer addressing, raw address materialization is rare — most memory access uses capability tokens and tiny pointers, both fitting in 16-bit immediate loads. When large constants are needed, SEER uses an assembler-managed literal pool.

Scoring methodology

literal pools — whether compiler must emit out-of-band data (SEER: assembler-managed, transparent)
register pressure — scratch registers consumed during materialization

Why register count is the dominant spill factor

The byte-alignment argument. Objection to 255 registers: "you're wasting register address bits on hardware with fewer physical registers." The answer: SEER requires byte-aligned fields throughout — every register operand occupies exactly one byte regardless. On hardware with 16 physical registers, the top 4 bits of that byte would be padding. SEER puts them to work instead. The "wasted bits" were never available to spend elsewhere. Maxing out the register space to 255 is free.
Design Claim · 03
Heterogeneous Dispatch
A single bitmask check at decode time replaces the entire CPU-GPU runtime stack. The question is not just which workloads become faster — it's which ones become viable at all.

Dispatch overhead = everything between a CPU deciding to run something on another unit and that unit actually starting. CUDA: 5–50 µs. SEER bitmask routing: ~30 ns theoretical — the AND + compare itself is ~2 ns, with the remainder accounting for clock-domain crossing into the target tier.

Caveats

Scope of the determinism guarantee. SEER's single-cycle, non-speculative timing guarantee describes the core scalar path — SYS, control flow, ARITH, and capability-authenticated LI+MEM accesses — the path a safety-critical control loop actually executes on. The GPU/warp tier (VMEM/AMEM/WARP/DISP: texture, dispatch, and barrier ops) is intentionally variable-latency, trading determinism for parallel throughput on workloads — vision, sensor fusion — that sit outside the certified control loop, not inside it. The ~30 ns figure below measures the cost of the bitmask decision to hand work to that tier, not the cost of the work once it's there; it should never be read as evidence that dispatched GPU-tier work is itself fixed-latency.
SEER figure is theoretical, and now includes domain-crossing cost. The AND + compare itself is single-digit-ns logic, but if the GPU/warp tier lives in its own clock domain — likely, given the tier-independent power-gating story — reaching it needs a synchronizer and some pipeline fill before execution actually starts. ~30 ns is a more honest estimate of that total than the bare gate delay; it still assumes a shared register file or coherent memory reachable without a copy. Real silicon could still move this number in either direction once interconnect and synchronizer designs are fixed.
CUDA/OpenCL overhead is measured. The 5–50 µs range reflects real launch overhead on modern discrete GPUs, varying by driver, kernel complexity, and argument marshalling.
The viability point matters more than the speed point. Fine-grained tasks (sort 200 elements, hash 32 bytes, compress one block) are currently CPU-only not because GPUs are slow at them but because dispatch overhead exceeds their runtime. Near-zero dispatch makes these economical to offload.

~1–5%
Industry-shaping
Where ARM and RISC-V live. Requires either a black-swan event — a Spectre-class vulnerability in the dominant ISA that SEER would have prevented — or 10–15 years of patient market development.
The honest summary. The two middle-and-low outcomes — niche business or modest exit — together hold the majority of the probability mass. Industry-shaping is a real but small tail, and reaching it depends far more on patience and external events than on any single design decision.
