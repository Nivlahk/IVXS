Random stress test

Generates a random program exercising ALU ops, branches, nested loops, function calls, and memory ops through the boot-time capability -- loads it into Source above, compiles it, and runs it through the simulator to confirm it halts cleanly before you send it to hardware. Same seed always regenerates the exact same program, so a failure can always be reproduced. Every register the program can read is explicitly zeroed first, so results never depend on leftover register state from a previous run -- the FPGA's register file is only initialized at bitstream configuration, not by reset.

Settings

How many registers seer_regfile.sv actually has real storage for on the hardware you're targeting (must be a power of two, 4-256 -- confirmed 2026-07-20: a mismatch here, not caught anywhere before, silently trapped every single program using a function call). The compiler places its special registers (ra/fp/sp, retry counters, the symbolic auto-allocation pool) relative to this depth, so the high-level features keep working at any depth of 16 or more. The simulator, the stress-test generator, and the hardware-capture validator all enforce the same rules real hardware does: zr (r255) is always hardwired-zero at any depth, register depth-1 is the depth's own local hardwired zero (seer_regfile.sv's ZR_IDX -- reads 0, writes discarded), and any other register at or above this value raises the same illegal-instruction trap real hardware would.
Off (default): the four toggles below only change what the Assembled panel shows -- the Source box keeps whatever you typed. On: checking one of those toggles rewrites the Source box itself with the result of that transform (e.g. checking control-flow abstraction expands your if/while into flat jeq/labels right there in the box), then unchecks itself so the box is holding real, editable SEER assembly at the new altitude -- each check is one deterministic step down in abstraction, not a live/reversible view. Turn this off again to go back to leaving Source alone.
Write names instead of rN (e.g. add acc, val, one) -- each distinct name gets a register automatically, freed for reuse once the name's last use has passed. The underlying linear-scan algorithm is straight-line by construction, but a name whose value is genuinely single-assignment (written once, or written in mutually-exclusive if/elif/else branches so only one write ever executes) is provably safe across a loop back-edge too, since there's no reassignment for the back-edge to corrupt -- confirmed the existing algorithm was never actually wrong for that case, only for a name genuinely reassigned inside a loop body. When used alongside control-flow abstraction below, the warning narrows to name the specific reassigned-inside-a-loop names actually at risk, instead of a blanket "this program has a branch" message. Without control-flow abstraction (hand-written jeq/labels), there's no branch structure to analyze this way, so the original blanket warning still applies. Reserved aliases (zr/sp/fp/ra) and explicit rN registers still work as-is and are never auto-assigned.
A capability register (cap_reg) may only be touched inside a matching use rN: block; li.captr rN, ... initializes it, ld64/ld.s32/ sts32/sts64 require it already initialized. call foo() lend rN makes rN unavailable for exactly that one call, reverting automatically once it returns. Off by default -- existing capability code with no use/lend anywhere is unaffected either way, but turning this on is what actually enforces the discipline rather than silently allowing unwrapped capability touches to pass.
retry N: ... onfail: ... attempts the body up to N times; succeed inside the body exits the whole construct immediately, skipping any remaining attempts AND the (optional) onfail block. If every attempt runs without hitting succeed, onfail runs once (not retried) before continuing. Uses a dedicated counter register per retry, reserved from r245-r251 -- separate from the auto-allocator's r0-r199 range specifically to avoid collision if symbolic register names are also in use; nesting deeper than 7 retries throws a clear error rather than silently reusing a register. break N exits N enclosing loops at once (plain break still means N=1) -- for aborting an entire nested maneuver from deep inside, not just the innermost loop.
Write high-level control flow directly in the Source box above; every jump offset is computed automatically by counting nops between two points in the compiled program (confirmed correct via direct RTL tracing this session -- a branch landing on a connector node always lands past it, and a natural fall-through fetch of the same node costs the identical one unit, so any two paths converging on a point always agree, regardless of runtime history). Composes with symbolic register names above -- both apply together, control-flow compiling first so instruction lines (with names still intact) pass through to the register allocator afterward.

Function calls (def name(): / call name()) are supported. As of 2026-07-13, calls are TABLE-ADDRESSED, not register-computed -- jmpr was abandoned as the call mechanism after its live 64-bit target-address add was identified as the one Fmax watch-point on the redirect path; a function's entry point is now an ordinary registered connector node (exactly like a label), reached via a linking jmp that reuses the same cheap CN-table lookup every ordinary jump already goes through, with no live address computation on the critical path. The counter-isolation mechanism that makes functions composable is unchanged and still confirmed real: the linking jump resets cn_count to 0 for the callee, and ret restores the caller's exact saved value on return -- every function gets independent label numbering with zero coordination needed between caller and callee, no matter how deep the call nesting. jmpr itself is kept in the ISA, fully functional, simply unused by convention -- nothing generates it anymore, but hand-written code using it directly still works. One consequence worth knowing: calls can only reach compile-time-known targets now (like labels), not computed/indirect ones -- function pointers and virtual dispatch are what's given up in exchange for calls being as fast as branches.

Byte-editing is disabled while this is on -- a single high-level line can expand into many compiled lines plus a prepended setup section, so there's no sound way to map an edited byte back to a specific source line. Edit the high-level source and recompile instead.
Condition syntax: reg OP reg where OP is one of == != < >= <u >=u > <= >u <=u (u variants are unsigned; >/<=/>u/<=u are derived by operand swap -- the ISA's branch instructions only have ==,!=,<,>=,<u,>=u natively). Conditions compare two REGISTERS only -- the branch format has no immediate field; load a constant into a register first if you need to compare against one.

Every jump's offset is computed automatically by counting nops between two points in the compiled program -- confirmed to work this way from direct RTL tracing this session (a branch landing on a connector node always lands PAST it, and a natural fall-through fetch of the same node costs the identical one unit -- so any two paths converging on the same point always agree, regardless of runtime history). You never write a raw offset; the compiler counts for you.

Function calls are NOT included in V1. jmpr's CFI landing validation was traced directly and confirmed to be a stub (the signal that's supposed to trigger it, jmpr_taken, is produced but never consumed anywhere), and its interaction with the nop-counting model is unresolved. This compiler only emits the control-flow instruction family (jeq/jne/jlt/jltu/jge/jgeu/jmp) plus a one-time setup prologue that registers every label into the CN table before the real program runs.

Hardware target

SEER's 256-deep capability-secure register file, connector-node branch encoding, and capability/control-register ops have no lossless x86-64 equivalent, so this is a scoped, best-effort translation, not a full backend:
• Encoded for real (actual REX+opcode+ModRM bytes): add/sub/and/or/xor/mul and their *i immediate forms, shifts, li, jmp/jeq/jne/jlt/jltu/jge/jgeu, ret, nop, hlt -- and only for SEER registers r0-r12 (mapped to rax/rcx/rdx/rbx/rsi/rdi/r8-r14; r15 is reserved as scratch for lowering 3-operand SEER ops to x86's 2-operand form) plus zr.
• Flagged, not guessed: any register ≥13 (SEER routinely uses far more than x86 has), and every capability (ld/st/use/lend), control-register, bit-manipulation, and float-unit op -- these are architecture-specific and shown with a note instead of fabricated bytes.
• Branch targets are resolved by re-deriving the target line from the same nop-counting rule this tool already uses for SEER's own connector-node offsets (see the note above), then computing a real x86 rel32 against the x86 byte stream -- independent of SEER's own CN-table addressing.

Simulator

Executes the assembled bytes directly in the browser -- no hardware needed. Built fresh for this tool rather than porting the Python reference interpreter (seer_run.py), which is confirmed stale in two separate ways (an old load-opcode mapping, and no knowledge of ones'-complement offsets or table-addressed calls). Coverage: ARITH-R/I, the li family, ld/st, popcnt/clz/bset/btst, all control flow, wrctrl/rdctrl, li.cn/li.cn.reg. Anything else reports "unimplemented" and stops rather than guessing.

Automated Soak Test

Uses the same connection as the floating "Connect FPGA Hardware" button (or the Connect button above -- they're the same connection now). Each iteration: generates a random program, sends it, listens for trace_packetizer's live write-back frames, and compares them against the simulator -- no ILA capture needed.

Reset is still manual. The loader FSM's "done, core running" state is only left by a fresh cpu_resetn assertion (see seer_top.sv), and nothing here can trigger that in software -- so each iteration pauses and waits for you to press the board's physical reset button before it sends. Everything else (generation, sending, comparison, logging, moving to the next seed) is automatic.

Known fidelity limit (2026-07-24 redesign): trace_packetizer now sends the final value of each register once, coalesced in hardware (a 256-entry table indexed by register address, updated in place on every write), instead of every intermediate write -- this checks the full 64-bit final value per register against the simulator, not just a truncated 16 bits, but it genuinely cannot see a wrong intermediate write that gets silently overwritten by a correct one before anything reads it. That's a real blind spot, not a rounding error -- it's the same shape as the actual dcache write-combining bug found earlier in this project (wrong data sitting in a line, silently corrected by a later store before anything read it). Good for catching "did this random program's final state come out right" across many runs; not a substitute for occasional deeper per-instruction checking.

Trap/Exception Soak Test

Same connection and comparison mechanism as the Automated Soak Test above, but a different generator: each iteration deliberately triggers one of several trap causes (illegal instruction / privilege violation / arithmetic / syscall / debug / capability auth failure), places a matching handler at the real IVT offset for that cause, and checks -- via ordinary register writes, so the same per-register comparison applies unmodified -- that the handler actually ran and execution resumed cleanly afterward. Exercises code this tool's main generator never touches at all (traps have no architectural effect in the plain simulator), so this bar predicts expected outcomes analytically instead of via simulateProgram.

Adversarial Capability Input Soak Test

Installs one legitimate capability, then attempts a randomly-chosen kind of invalid access against it: a stale generation (post-revocation), a directly corrupted mac, a token pointing at an uninstalled index, an in-bounds-looking-but-out-of-range pointer, or a write attempt through a read-only capability. Each iteration checks two things, not just one -- that the attack is actually rejected (traps with the expected cause), and that a legitimate, separate access afterward still reads back the correct, unmodified value -- the real security assertion, not just "did something trap". Same connection and per-register comparison mechanism as the other two panels.

One instruction per line. Comments after ; or #. Registers: r0–r255, or zr(255) sp(254) fp(253) ra(252). Hover any byte for its field meaning. 1-byte terminals (sei/cli/sysret/hlt/nop/ebreak/ecall/wfe) encode to a single byte; everything else is 4 bytes, big-endian, [opcode, b1, b2, b3].

Cycle counts are per-instruction issue cost, built from actual RTL/testbench evidence: 1 cycle default, 2 for clmul/crc32 (noted in source), 4 for memory ops (ld64/ld.s32/sts32/sts64/li.64 -- measured in the passing ISA testbench, hit and miss identical). A few ops (dcf.*/ics/io/vxchg/rdrnd/tlbi/hprobe/dcz) have no confirmed cycle count in this project's evidence and are marked ? rather than assumed. The total shown is straight-line cost only -- it does not model branches actually taken or memory stalls beyond the base 4.

Download produces the exact file seer_top.sv's UART loader expects: a 4-byte big-endian word count, then the program's bytes densely packed (no padding between instructions — confirmed against seer_imem.sv's actual byte-addressable fetch path, which reconstructs a fetch from any byte offset via rd_bs=addr[1:0], not just word-aligned ones). A 1-byte terminal does NOT get its own word; a following 4-byte instruction can start mid-word. This file is already correctly ordered -- send it directly (copy /b or a raw serial send); do not run it through the LLVM-toolchain byte-swap step, which corrects a different tool's quirk and would corrupt this file instead.

Disassemble (button next to Assemble) reverses the process: paste hex into the Source box above and click it -- it auto-detects the 4-byte word-count header (tries with it first, falls back without) rather than needing a manual toggle, and always uses the correct compact byte-stream interpretation for real data (a downloaded file, an actual imem dump, raw assembler output). Also strips up to 3 trailing sei instructions if present at the very end -- those are almost always packDense's trailing zero-padding decoded as a real opcode by coincidence (sei=0x00), not an actual instruction; a program genuinely ending in sei would be unusual since nothing runs afterward to benefit from it. Word-aligned parsing was dropped in this consolidation, since it's only valid when the data is already known to be word-aligned throughout -- not generally true for real programs containing any 1-byte instruction that isn't the very last thing in the file.
